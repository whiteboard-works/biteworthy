2026-10-12 (UTC) — **The assistant can ask a question now, and get back an answer rather than a string.** Built 2026-08-14 on `feat/ask-questions` (#598) and parked as a draft; rebased across two months of master and finished today. The case for the feature is narrower than "let the model ask things" — the model could always *write* "did you mean the taqueria or the cantina?" and wait. What comes back then is `"the first one"` or `"taqueria"` or `"yes"`, and it has to guess which option that was, with every downstream call resting on the guess. `ask_questions` has the server write the options down, the client render exactly those, and the answer return as an **option id**. An id that is not on the stored list is refused rather than quietly accepted as free text — that refusal *is* the feature. A free-text escape hatch stays and is marked as the person's own words, because an option list that misses the obvious answer is worse than no options at all. **`halts_turn` is the general mechanism** and is deliberately not part of `ModePolicy`: halting is not a permission decision and applies in every mode. Parking happens on the *decision* to call, before dispatch — the same shape as a confirmation and for the same reason, since this call's `tool_result` has to be the person's answer and so must not already exist. A malformed question (one option, duplicate ids, a non-object option) comes back as a recoverable tool error rather than parking, because a park nobody can clear needs a human with database access. The second parked state: `Conversation::STATES`, a rewritten CHECK constraint (Postgres has no ALTER that adds a value), `pending_questions`, `Conversation#parked?` replacing the `awaiting_confirmation?` checks that all meant "is this turn still owed a reply", `POST /answer`, the serializer, the SSE terminal type, the rswag path, and both clients. **Finishing it found a deadlock the August version shipped with.** A message queued just before a park was held by putting it back at the head of the queue — and the answer that would un-park the conversation is appended *behind* it, so the job popped the message, held it again, released, and never reached the answer; the stream also kept the connection open on the held message. `next_pending_turn!` now pops the first *runnable* turn (while parked, only a `confirm` or an `answer`), and `runnable_turns?` is what the stream relay and the sidebar's working mark ask instead of `pending_turns?`. Codex's August review held nine findings that still applied after the rebase and are fixed here: both clients gated the composer and the queue drain on `pending` alone, so a parked question let a queued message hit a 409; the web analytics outcome and the relay's terminal list did not know the new event; a new chat kept the old chat's question on screen; the free-text answer skipped the 20,000-character ceiling a message has; the rswag path documented no 202; the migration's rollback would fail while anyone had a question open (parked rows are normalized first now); and `fingerprint` is required in the contract since the loop refuses an answer without one. Migration renamed to today's timestamp so it sorts after everything that shipped in between. **The local review then found the sharper one**: every tool call the model queued *behind* `ask_questions` in the same message was still run once the person answered — decided before the model had the answer, and in `accept_edits` or `auto` a write against the guess the question existed to avoid. Those calls are answered as `skipped` at park time now, and the model re-issues whichever it still wants after reading the answer. Also from that pass: option ids and details are stored as strings (a numeric id could never match its own button), more than five options is refused like fewer than two, the fingerprint carries a nonce so the same question asked twice cannot be answered by a tab showing the first, a second tap on an option (or a confirm from a tab that was behind) is dropped by the queue instead of raising in the loop and failing the job, the controller refuses a non-string `option_id` or a missing fingerprint synchronously, the park emits its `tool_use` event so the live card reads "Asking you a question", `halt` clears `pending_questions` with `pending_tool_call`, and `ask_questions` is not offered over `/mcp`, which has no loop to park and nobody to ask. Two findings declined: compaction eliding the stored answer in a long chat (the model's follow-up already encodes what it did with the answer, as with every other elided result, and the placeholder tells it to ask again only if it still needs to), and showing the person's answer as its own transcript bubble (a user text block beside tool results muddles the transcript; the model's follow-up names the choice). Branch `feat/ask-questions`.
