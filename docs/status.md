tick or significant event. Format:

```

```

The point is breadcrumbs: a tick interrupted at minute 28 should leave
enough here for the next tick (or a human dropping in) to resume
without spelunking GitHub.

2026-08-13 23:55 (UTC) — **Long conversations stop re-sending every menu they ever fetched — and the cost case for it is not the one the task assumed.** The premise on file was that `tool_result` blocks are 66% of the largest transcript, so eliding them is the win. The byte share is right (measured again: 59% and 66% of the two largest, 97k and 83k tokens) but the money does not follow from it. Those stale results sit inside the *cached* prefix and are read back at 0.1×, so eliding them saves roughly 6% of a warm turn's input cost against a one-off re-write of the compacted prefix at 1.25× — about eighteen turns to pay back, which is longer than conversations actually run. **Where it does pay is the cold turns**, and that only shows up by crossing two measurements: the ephemeral cache lasts five minutes and 9 of 28 gaps between turns in one conversation are longer than that, so about a third of turns re-write the entire transcript. Resuming a 97k-token conversation costs 121k input-equivalent tokens; a compacted one costs 71k. Payback lands near four turns, and the $10 ceiling stops arriving mid-thought — which is the failure people actually feel, since a conversation that dies takes with it the context that made it expensive. So: `Chat::Compaction` marks messages outside the last 20 whose tool results have gone stale, and `Conversation#content_for` swaps those results for a placeholder on the way to the API. **The rows are never edited** — the clients render `conversation.messages`, so compacting by rewriting would delete a person's record of what happened; the marker is a projection and clearing the column undoes it. Three choices worth keeping: it **elides rather than summarizes**, because every `tool_use` survives, so the model can see it asked and simply ask again — a summary cannot be re-derived and can be wrong about what it dropped, and it would cost a model call for a decision code can make (Rule 5). It is **persisted rather than recomputed**, which is the property the whole design turns on: a rule evaluated live would elide a different set as the conversation grew, moving bytes above the prompt-cache breakpoint and re-writing the transcript on *every* turn — spending the cost it exists to avoid, forever. And the window is **20 messages, not 10**, because the curve is flat there — keeping 10 elides 43% of transcript bytes and keeping 20 elides 41%, so the extra ten cost two points and buy a much wider margin against the case that actually hurts, which is eliding a result the model is still working from (a scan flow polls `get_scan_status` eight times running). It is **announced**, per the original ask: one narration line on the turn it happens, on both clients, because silently dropping data the model was working from surfaces later as the assistant mysteriously forgetting a menu it had already read, and a person who was not told has no way to connect the two. The query-count guard earned its keep — compaction runs before the first model call and was loading the messages separately from `transcript`, a second full load of everything the turn was about to read; `Conversation#stored_messages` is now the one memoized loader for both. Fifteen new examples, mutation-checked — and **two of them passed their first mutation and had to be rewritten**: the recent-window spec had no tool result inside the window, so "keeps the last 20" and "compacts everything" were indistinguishable, and the second-call guard was never reached because the transcript fell under the threshold after one pass. 1,802 API examples green, 437 web, 134 mobile, rubocop clean, brakeman 0. 2026-08-13 22:40 (UTC) — **The clock was throwing away the conversation cache, and the fix that was supposed to stop it only made the loss intermittent.** Measured on production first, read-only, because the open task asserted the opposite premise: that human-paced turns land more than five minutes apart so the cross-turn cache almost never hits. It is wrong — the median gap between consecutive runs in one conversation is 125 seconds and 19 of 28 are under five minutes, and 72.3% of input tokens are already cache reads. What the numbers actually say is that **cache writes are 65.8% of input cost** (reads 18.0%, uncached 16.2%), so the question was never "how do we hit more often", it was "why are we writing so much". Answer: a `messages` breakpoint's prefix is `tools → system → messages`, so the volatile system block sits above the transcript and any change to it re-writes the whole conversation — and `current_time` lived there, bucketed to five minutes on the reasoning that precision finer than the ephemeral TTL cannot help a cache. Half right. A bucket flips on **wall-clock boundaries**, not on how long ago the last turn was, so two messages forty seconds apart straddle 16:04:59 / 16:05:01 and the second pays in full. 4 of 19 follow-up turns sent *inside* the cache's own TTL crossed a boundary like that, and those turns spent 27% of their input on cache writes against 6% for the ones that did not. The clock is out of the system prompt entirely now: `AgentLoop#clocked` appends it after the block `cacheable` marked, which is below every breakpoint and so in no cached prefix at all — the invalidation goes to zero and, because nothing downstream of it is cached any more, it goes back to second resolution and drops the "approximate" label it was only carrying for the cache's benefit. The other candidate, **widening the ephemeral TTL to an hour, is a straight loss and is now written down as one** (C-D7): it prices every write at 2× instead of 1.25× when writes are already the dominant line, to rescue only the 5 of 28 gaps that fall between five minutes and an hour. Two existing specs encoded the old shape and were rewritten rather than deleted — "moves the clock on once the bucket has passed" was pinning the bug, and the two breakpoint specs asserted the mark lands on the *last* block, which is now the last *stored* block with the clock deliberately after it. Four new examples: the system array is byte-identical across a one-hour gap, two turns straddling a five-minute boundary keep both the system array and the cached prefix, the clock is below the breakpoint and absent from the system prompt, and the time is stated to the second. Mutation-checked by moving the clock back inside the marked prefix (`cacheable(clocked(…))`), which fails three of them. 240 chat + conversation examples green, rubocop clean. 2026-07-16 — Deploy-api host-key pinning. Branch `fix/deploy-api-pin-host-keys`.

- **The 6de948a deploy failed** with `Net::SSH::HostKeyMismatch … fingerprint
  SHA256:GlR1Zi0t… does not match`. The box has not been rekeyed: all three of
  its current fingerprints (rsa/ecdsa/ed25519) equal the entry in the
  maintainer's local `~/.ssh/known_hosts`, and the "mismatched" key is the
  box's *real* ed25519 key. Scope that evidence honestly — there is **no
  checked-in provisioning fingerprint record**; the laptop entry is itself
  TOFU-established, so this shows only "unchanged since first connect", and a
  host-key comparison is **not** a compromise assessment either way. The
  a701eea run had SSH'd fine 7 min earlier on identical logic (6de948a changed
  only comments), so the failure was nondeterministic.
- **Root cause — a race in `ssh-keyscan -H`, reproduced both ways locally.**
  Nothing was wrong with the box's keys and nothing was intercepted:
  - `ssh-keyscan -H` writes rsa/ecdsa/ed25519 in network **arrival order**.
  - Kamal → SSHKit, and SSHKit **replaces net-ssh's known_hosts matcher** with
    its own (`backends/netssh.rb`). Its `KnownHostsKeys#keys_for` **returns on
    the first matching hashed entry**, so a hashed file yields exactly **one**
    key type — whichever won the race.
  - rsa first → SSHKit yields only the rsa key → net-ssh negotiates ed25519 →
    compares it against the lone rsa entry → `HostKeyMismatch` naming the box's
    *real* ed25519 fingerprint. **ed25519 first → verifies, deploy proceeds.**
    Same code, two outcomes, 7 min apart — exactly a701eea (pass) vs 6de948a
    (fail).
  - Plaintext entries yield *all* types for the host (`keys[h]`), so they can't
    lose this race. That is why pinning fixes it.
- **Two earlier hypotheses were wrong; recorded so the next reader doesn't
  re-run them.** (a) "Empty/partial scan" — refuted: empty known_hosts is
  silently *accepted* (net-ssh accepts a host it has no entry for), and a
  truncated line raises `ArgumentError`, so neither yields this error.
  (b) "The scan returned a wrong key, so interception can't be ruled out" —
  **withdrawn**: it came from probing `Net::SSH.start` directly, which uses
  net-ssh's own matcher and returns *all* matching keys. Kamal never takes that
  path. Probing SSHKit's matcher — the real consumer — reproduced the failure
  from correct keys alone. No security event.
- **Fix:** pinned **plaintext** host keys via a new `SSH_KNOWN_HOSTS` repo
  secret (3 lines, all types); dropped the scan; `set -euo pipefail` +
  preflight. The guard calls **SSHKit's own `KnownHosts#search_for`** rather
  than imitating it with grep/`ssh-keygen -F`, so the check cannot disagree
  with the deploy: both regex and `ssh-keygen -F` *passed* wildcard and
  `@cert-authority` pins that SSHKit yields **zero** keys for — a green check
  over an unverified deploy — and the regex also *blocked* valid rsa/ecdsa
  pins. It also rejects hashed pins outright, since those reintroduce the
  first-hash-only race that caused this incident. Verified against the live
  box: the pin resolves to 3 keys and passes; wildcard/`@cert-authority`/empty
  are blocked. Re-pin *only* from out-of-band-verified material, unhashed —
  never from a bare `ssh-keyscan`. See the note in `deploy-api.yml`.
- **Known gap — the guard looks the host up exactly as Kamal does *today*.**
  net-ssh derives its lookup key from the connection, so changing
  `apps/api/config/deploy.yml` can silently move it out from under the pin:
  `ssh: port:` → `[ip]:port`; an `ssh: proxy:` or a DNS hostname in
  `servers.web.hosts` → `host,peer_ip` (SSHKit intersects the per-name key
  sets, so a single-host-field pin yields **zero** keys). Zero keys means
  Kamal accepts the host unverified while the guard still prints OK. If any of
  those change, re-pin in the matching form. The guard fails closed on
  everything it can see; it cannot see deploy.yml.
- **Method note:** probe the client the code actually uses. Driving
  `Net::SSH.start` directly produced confidently wrong conclusions twice,
  because SSHKit swaps out the matcher underneath Kamal.
- Gitignored `biteworthy-deploy{,.pub}` (the CI deploy keypair, root on the
  API box) — it was sitting untracked and uncovered in the repo root. History
  checked: never committed. **MANUAL, user: move that keypair out of the repo
  (e.g. `~/.ssh/`); the gitignore is only a backstop.**
